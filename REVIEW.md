# REVIEW.md

List every defect you found in the starter `app/main.py` (helpers and endpoints). For each one:

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes` (lines 33-38) | Grace period logic checked `minutes > 10` after integer division. For 10m 1s past shift start, `int(601 / 60) = 10`, so condition evaluated to False and returned 0 instead of 10. | Punching in at 09:40:01 IST for a 09:30 shift returned 0 late minutes instead of 10 (violating R2). | Checked elapsed seconds directly: `if diff_seconds > 600: return diff_seconds // 60`. |
| 2 | `compute_late_minutes` (lines 33-38) | Timezone mismatch: compared UTC `punch_in` directly with IST `shift_start` using naive replacement, producing erroneous or negative differences. | Punch-in at 09:30 IST (04:00 UTC) was compared against 09:30 UTC, producing -330 minutes. | Converted `punch_in` to IST timezone before calculating difference against IST shift start. |
| 3 | `compute_late_minutes` (lines 33-38) | Did not handle overnight shifts where punch-in after midnight belongs to the shift starting the previous calendar day (R1). | Punch-in at 00:30 IST for a 22:00-06:00 shift computed late minutes against 00:30 on the current day instead of 22:00 previous day. | Integrated `determine_attendance_date` to anchor shift start to the correct attendance date. |
| 4 | `compute_work_hours` (lines 40-41) | Python's built-in `round()` uses round-half-to-even (banker's rounding) rather than round half-up (R4). | Duration of 16,182 seconds (4.495 hours) rounded to 4.49 instead of 4.50. | Used Python's `Decimal` with `ROUND_HALF_UP` quantization to 2 decimal places. |
| 5 | `compute_overtime` (lines 44-48) | Ignored the 30-minute threshold: returned minutes even when overtime was under 30 minutes (R3). | Punch-out 10 minutes after shift end returned 10 overtime minutes instead of 0. | Added threshold check: returned `diff_seconds // 60` only if `diff_seconds >= 1800` (30 mins), otherwise 0. |
| 6 | `compute_overtime` (lines 44-48) | Assumed shift end falls on the same calendar day as the attendance date, failing for overnight shifts (R1, R3). | For a 22:00-06:00 shift starting on 2026-07-06, shift end was computed as 2026-07-06 06:00 IST instead of 2026-07-07 06:00 IST. | Added 1 day to shift end date when `shift_end <= shift_start`. |
| 7 | `compute_overtime` (lines 44-48) | Subtracted timezone-aware IST datetime from potentially timezone-naive UTC datetime, raising `TypeError`. | Calling `compute_overtime` with PyMongo naive datetime raised `TypeError: can't subtract offset-naive and offset-aware datetimes`. | Ensured all datetimes are timezone-aware and normalized to IST for shift calculations. |
| 8 | `health` (lines 72-74) | Unconditionally returned 200 without checking if MongoDB is reachable; failed to return 503 when database is down. | Stopping MongoDB service still resulted in GET `/health` returning 200 OK instead of 503. | Pinned readiness check to `client.admin.command("ping")`, catching exceptions and raising 503. |
| 9 | `create_employee` (lines 77-85) | Race condition: relied on check-then-insert (`find_one` then `insert_one`), allowing concurrent duplicate creates to both succeed. | Parallel requests creating the same `emp_code` created duplicate records or 500 errors. | Created a unique index on `emp_code` at startup and caught PyMongo `DuplicateKeyError` to return 409. |
| 10 | `create_employee` (lines 77-85) | Allowed `shift_start == shift_end`, violating OpenAPI contract. | Submitting `shift_start: "09:30"` and `shift_end: "09:30"` returned 201 instead of 422. | Added validation checking `body.shift_start == body.shift_end` and returning 422. |
| 11 | `create_employee` (lines 77-85) | Serialized `created_at` as ISO datetime string instead of integer epoch milliseconds (`EpochMillis`). | Response schema validation failed because `created_at` was a string, not an integer >= 100000000000. | Converted `created_at` to integer epoch milliseconds before returning. |
| 12 | `EmployeeIn` (lines 53-61) | Missing schema constraints: did not validate `emp_code` pattern (`^EMP\d{4,6}$`), email format, string lengths, or calendar date format. | Sending `"emp_code": "INVALID"` or invalid emails was accepted with 201 instead of 422. | Applied strict Pydantic v2 Field validators and regex patterns matching `openapi.yaml`. |
| 13 | `list_employees` (lines 88-96) | Off-by-one pagination bug: `skip = page * page_size` skipped the entire first page when `page = 1`. | Requesting `page=1&page_size=20` skipped the first 20 employees. | Corrected offset calculation to `skip = (page - 1) * page_size`. |
| 14 | `list_employees` (lines 88-96) | `total` count ignored query filters: `db.employees.count_documents({})` counted the entire collection (violating R10). | Filtering by `department=Engineering` returned total count of all employees across all departments. | Passed filter dictionary `q` to `count_documents(q)`. |
| 15 | `list_employees` (lines 88-96) | Did not sort by `emp_code` ascending as required by API contract. | Employee list items were returned in arbitrary MongoDB natural insertion order. | Added `.sort("emp_code", ASCENDING)` to the cursor. |
| 16 | `punch_in` (lines 99-123) | Crashed with 500 `TypeError` when `emp_code` did not exist instead of returning 404. | Punch-in request with non-existent `emp_code` raised unhandled `TypeError: 'NoneType' object is not subscriptable`. | Checked `if not emp: raise HTTPException(404, "Employee not found")`. |
| 17 | `punch_in` (lines 99-123) | Race condition: relied on check-then-insert for existing punch-in on date, allowing duplicate punch-in records under concurrency. | Concurrent identical punch-in requests created multiple records for the same employee and date. | Created a unique compound index on `(emp_code, date)` and caught `DuplicateKeyError` to return 409. |
| 18 | `punch_in` (lines 99-123) | Determined attendance date from UTC/local time instead of IST calendar date and ignored overnight shifts (R1). | Punch-in at 01:00 IST for a 22:00-06:00 shift was assigned to the current day instead of the previous day's shift. | Implemented `determine_attendance_date` with overnight shift logic. |
| 19 | `punch_in` (lines 99-123) | Did not truncate instants to whole seconds before calculation and storage (R1). | Milliseconds and microseconds were persisted into MongoDB and returned in responses. | Truncated epoch milliseconds to whole seconds `(ms // 1000) * 1000` before processing. |
| 20 | `punch_in` (lines 99-123) | Included internal `"id": str(res.inserted_id)` in the response body, violating the OpenAPI schema. | Response validation failed against `AttendanceRecord` schema which has no `id` field. | Formatted document strictly according to schema without any internal IDs. |
| 21 | `punch_in` (lines 99-123) | Accepted invalid statuses (e.g. `ABSENT`, `LEAVE`) and did not validate `punched_at` timestamp range. | Submitting `"status": "LEAVE"` or seconds-looking timestamps was accepted. | Restricted status to `PresenceStatusEnum` (`PRESENT`, `WFH`, `ON_DUTY`) and validated timestamp range. |
| 22 | `list_attendance` (lines 124-151) | Memory / performance defect: fetched all documents into Python memory `list(db.attendance_logs.find(q))` and sorted in Python. | Severe latency and memory spike on 100k records. | Replaced with database-level `.sort()`, `.skip()`, `.limit()`, supported by compound indexes. |
| 23 | `list_attendance` (lines 124-151) | Missing secondary sort by `emp_code` ascending. | Records with identical dates were returned in indeterminate order. | Added secondary sort: `.sort([("date", DESCENDING), ("emp_code", ASCENDING)])`. |
| 24 | `list_attendance` (lines 124-151) | Missing validation that `date_from <= date_to`. | Querying `date_from=2026-07-10&date_to=2026-07-01` returned empty list with 200 OK instead of 422. | Added check raising 422 if `date_from > date_to`. |
| 25 | `list_attendance` (lines 124-151) | Returned `"id": str(d.pop("_id"))` and failed to convert datetime timestamps to epoch milliseconds. | Returned documents had string IDs and ISO datetime strings violating schema. | Mapped all records using `serialize_attendance_record` converting instants to epoch milliseconds. |
| 26 | Startup (lines 22-24) | No database indexes created at startup; `MongoClient` missing `tz_aware=True`. | Unindexed collection scans (`COLLSCAN`) on list and analytics queries; PyMongo returning naive datetimes. | Added idempotent `ensure_indexes()` in FastAPI lifespan and initialized `MongoClient` with `tz_aware=True`. |

Also note anything you looked at and decided was **not** a defect, and why:

1. **`history` array initialized as empty `[]` on punch-in:** Examined whether initial punch-in should log an entry in `history`. Confirmed by section 4 of `DATA_MODEL.md` and `openapi.yaml` that `history` is strictly for manual corrections (regularizations via `PATCH`); initial punch events must never write to it.
2. **`work_hours` being `null` until punch-out:** Confirmed that R4 explicitly requires `work_hours` to remain `null` while a record is open without punch-out.
3. **Omitting `_id` from API responses:** Confirmed that `DATA_MODEL.md` explicitly specifies `_id` is an internal MongoDB detail that must never appear in API requests or responses.
